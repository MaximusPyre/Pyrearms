What you are building

Not a WordPress install. Not a headless CMS. A small React site where articles are TypeScript data, the edge host is Cloudflare, and a Cursor Automation opens one pull request a day with a finished post — news when it exists, related evergreen when it does not.

Vite + React Cloudflare Workers Typed blog posts Cursor Automations AdSense-ready slots JSON-LD / sitemap

Reference implementation: pyrearms.dev — education desk + map product + daily blog. This guide abstracts the pattern so you can point it at any niche.

The 15‑minute path

If you already have Node 22, a Cloudflare account, GitHub, and Cursor, this is the order. Do not rearrange.

0–3 min Scaffold + deploy shell
3–7 min Blog model + two routes
7–11 min SEO, home CTAs, ad slots
11–15 min Automation + cron + PR tool

  1. Scaffold the site

    Create a Vite React-TS app, add react-router-dom, wire Cloudflare via @cloudflare/vite-plugin + Wrangler. Deploy once with npm run deploy so the custom domain exists before you write content.

  2. Define posts as data

    One file (e.g. src/data/blog.ts) exporting BLOG_POSTS: Post[] — newest first. Render /blog and /blog/:slug from that array. No database for articles.

  3. Ship retention surfaces

    Home hero → primary product (map, tool, download) + blog. Latest post teaser on home. Article footer CTA back to the product. Sitemap + client meta / JSON-LD.

  4. Reserve ad slots safely

    Inline placeholders only at first. Never put empty ad-* rails in a CSS grid — blockers hide them and crush the article column.

  5. Attach the daily agent

    Cursor Automation on a schedule, repo = your main, tool = Open Pull Request. Prompt: follow a playbook file; one post per run; news or related topic; never “nothing happened.”

Stack (production shape)

Frontend

  • Vite + React + TypeScript
  • React Router for /, product pages, /blog
  • Articles compiled into the client bundle from TS modules

Edge

  • Cloudflare Worker serves the SPA assets
  • Optional D1 / admin API for non-content state only (sessions, bootstrap IDs) — keep user content off the clearnet worker if that is your threat model
  • Custom domain on the Worker

CI

  • GitHub Action: on push to main → npm run deploy with Cloudflare secrets
  • If Cursor auto-merges with GITHUB_TOKEN, also trigger deploy on that workflow finishing (token merges do not always fire push)

Blog as code

Treat the blog like a typed CMS you can grep. A durable shape: 

type BlogBlock =
  | { type: "p"; text: string }
  | { type: "h2"; text: string }
  | { type: "ul"; items: string[] }
  | { type: "quote"; text: string; cite?: string }
  | { type: "ad" }
  | { type: "cta"; title: string; body: string; href: string; label: string };

type BlogPost = {
  slug: string;
  date: string;          // "August 21, 2026"
  publishedAt: string;   // "2026-08-21"
  title: string;
  dek: string;
  hook?: string;
  tags: string[];
  sources: { label: string; url: string }[];
  blocks: BlogBlock[];
};

Agent rule: prepend the new post to BLOG_POSTS. Index page shows featured = first item. Article page maps blocks to HTML and always ends with a product CTA.

Do not let the agent invent court holdings, quotes, or membership coverage. Primary sources only when claiming news. Quiet days → related explainers with stable cites (docs you already trust).

SEO & retention

  • public/robots.txt + public/sitemap.xml listing home, product, /blog, and each slug
  • Client usePageMeta: title, description, OG, canonical, JSON-LD NewsArticle on posts
  • Home: brand-visible hero, one sharp line, CTAs to product + blog; below fold: one alert max + latest article + product loop
  • Articles: readable column (~40–44rem), share row, related posts, hard link back to the product

Retention is a loop, not a newsletter signup: read → check the product → come back when the next order drops.

Ads without breakage

Reserve slots early. Wire AdSense (or any network) later.

  • Use neutral class names like promo-slot — not ad-slot / advertisement on layout-critical wrappers
  • Prefer mid-article and index mid-roll placeholders; skip empty sticky side rails until real creatives exist
  • Why: many blockers set display: none on ad-* nodes. In a three-column grid (160px 1fr 160px), hidden rails leave the article in the first 160px track — one word per line. That is a real production bug. 
export function AdSlot({ slot }: { slot: "inline" | "index-mid" }) {
  return (
    <aside className={`promo-slot promo-slot-${slot}`} aria-hidden="true">
      <span className="promo-slot-label">Sponsor</span>
    </aside>
  );
}

// Later: replace inner markup with the network tag,
// keep the outer wrapper width-stable when empty.

AdSense checklist: site live on HTTPS, substantive original posts, privacy/terms links, apply when you have real traffic — placeholders alone will not approve you.

Cursor daily agent

In Cursor → Automations, create (or edit) a scheduled agent on your repo’s main branch.

Tools

  • Open Pull Request — required
  • Memories — optional
  • Comment on PR — optional; do not require approval bots

Playbook file in-repo

Commit something like docs/desk-agent.md the agent must follow. Core policy: 

One new blog post every run (prepend BLOG_POSTS).

1) Material niche news from primary sources → write that;
   update any alert banner; only edit product data if truth changed.
2) Otherwise → pick a related topic readers still need
   (deepen a recent post, spotlight one data row, explain one confusion).
   600–900 words + CTA to the product.
   Never invent facts. Never post “nothing happened.”

Open one PR on main.

Automation instructions (paste)

Follow docs/desk-agent.md (or docs/law-watch-agent.md) exactly.

One new blog post every run in src/data/… (prepend BLOG_POSTS).

1) Material news from primary sources → write that article;
   update alerts; only touch product/data files if the summary changed.
2) Otherwise → pick a related topic readers still need.
   Write a real 600–900 word explainer with a cta to your product route.
   Never invent holdings/facts. Never post “nothing happened.”

Open one PR on main. Education/marketing copy only — not professional advice
unless you are licensed and intentional.

On pyrearms.dev the playbook lives at docs/law-watch-agent.md. Same pattern, niche specifics filled in.

Cron that survives rate limits

Cursor schedules use UTC. Failures that die in under a minute with “Rate limited — too many concurrent runs” mean the cloud queue was full — usually at :00 on popular hours — not that your prompt is wrong.

  • Do not use 0 13 * * * (top of the hour)
  • Do use an off-minute daily job

Daily at 9:17 AM Eastern (EDT) = 13:17 UTC: 

17 13 * * *

Trap: 0 13 1 * * runs on the 1st of each month, not daily. If “Next run” jumps a month ahead, your day field is wrong.

In winter (EST) that same cron lands at 8:17 AM local. Move the hour if you care; consistency beats perfection.

Deploy loop

  1. Agent opens PR with the new post
  2. You (or auto-merge) land it on main
  3. GitHub Action runs npm run deploy
  4. Home + /blog show the new article

Optional cheap watchers (bill scrapers, RSS) belong in GitHub Actions + a small script, not inside the LLM agent. Keep the agent expensive only when it must read and write prose.

Launch checklist

  • □ Domain on Cloudflare Worker, HTTPS green
  • □ First three human-written posts (quality bar for ads + SEO)
  • □ Sitemap lists every slug; robots allows crawl
  • □ Home loops to product + latest post
  • □ Promo slots present; no empty ad rails in grid
  • □ Playbook committed; automation points at it
  • □ Cron off :00; test run succeeds once
  • □ Deploy Action secrets set; merge → live < 3 min
  • □ Privacy / terms if you apply for AdSense
  • □ Stagger other account automations away from this minute
